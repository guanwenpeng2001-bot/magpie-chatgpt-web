## Submitted-error classification investigation

The first GPT-5.6 automatic compaction's diagnostic at 13:20:07 UTC contained two older completed assistant groups and a final group with a user bubble and a visible seven-character service alert, but no assistant body. The snapshot intentionally omitted alert text; length does not prove its wording. `surfaceBound: false` measures the launcher surface marker, not response identity, so it cannot establish a rekey or lost assistant binding.

Source investigation identified a separate concrete classification gap: when a grouped response identity is unavailable and only its user-plus-alert group remains, ordinary reconciliation searches assistant identities. The existing scoped terminal detector can then miss the service error and DOM health eventually reports disappearance. Any fallback must authenticate the original submitted user message and exclude previous or competing turns; a page-global error search would be unsafe. This finding does not explain or repair the upstream service failure itself.

The explicit retry was passively instrumented through CDP response streams. All six requests used one resolved conversation. Requests two through six named parent IDs present among the previous response's assistant nodes. The first five selected GPT-5.6 Instant staging and the final request selected GPT-5.6 Pro. This supports client continuity for that retry. Response messages did not expose complete parent edges, so it is not proof of the entire server ancestry graph or full server-side ingestion. It does not retrospectively prove lineage for the earlier 276K trials.

The standalone instrumentation exports only hashed IDs, allowlisted metadata and counts. Its fourteen offline tests cover chunked UTF-8, root and patched message shapes, missing/conflicting identities, bounded buffers and exclusion of arbitrary content and credentials. Instrumentation is not itself a retention test.

## Fix scope and remaining gaps

The submitted-alert fallback runs after an established assistant binding disappears. It requires a unique new grouped user, original prepared-token or complete-text proof, a visible scoped service alert, no competing turn, and an unchanged DOM observation through proof and detection. Local multipart formatter provenance permits older staged messages to be virtualized. Text that merely resembles a multipart envelope grants no authority. It never installs a replacement assistant binding, changes tool authorization, retries a submission or weakens the reference's existing identity gate.

The follow-up also covers alerts before initial assistant selection. Still-present stale bindings/snapshots are not covered. Plain full-text proof without a prepared nonce requires baseline history to remain present. Copied recovery baselines do not inherit multipart provenance, and intervening DOM mutations cause abstention. These conservative limitations mean this patch does not claim to fix every live timeout above.

Four ports from reference commit `f08d16509e6a5447a0d0f2943abb172c69705160` address restored drafts, Mermaid preview remounts, strict UUID calendar inventories, and capability-menu activation. ## Broker diagnostics follow-up

The follow-up records only pinned-format broker registration/claim fingerprints, hashed trace identifiers and completion/retirement counters. It discards unrelated stdout/stderr, raw tokens, prompts and tool arguments. Each account keeps up to two generation-specific `broker-diagnostics-<timestamp>-<runId>.json` artifacts, with 128 events per snapshot and explicit dropped-record counters. Stream drain and optional final writes each have a 500 ms bound; timed-out writes are aborted and cannot overwrite a newer generation's file. Tests cover exit followed by final pipe data, stuck pipes, stuck writers, late write/rename completion and daemon alias cleanup. Cross-stream arrival order is not a strict causal ordering, and absence of an event from a truncated ring does not prove a token mismatch.

The combined initial-wait and diagnostics changes passed 1,494 serial tests: 1,492 passed, zero failed, two skipped, with the pinned reference/compaction smoke options and installed Chrome enabled. Independent review approved both changes; the diagnostics-focused set passed 45/45. Clean-package validation scanned 57 packaged files. These checks establish offline behavior; renewed live tool/compaction validation remains required. Local regression evidence is `native-live/release-056/combined-full.log`.

## Automatic compaction identity ordering

A fresh GPT-6 Sol automatic-compaction trace on 2026-11-14 completed its actual read/test command (exit 0), then failed to continue. Content-free boundary fingerprints showed unchanged model, effort (high), thread, turn and user item identity. The client's task content was unchanged. Inside the pinned runtime the normal request's `[{type,text}]` and compact request's `[{text,type}]` had different raw JSON hashes; an offline calculation reproduced both observed hashes exactly. The resulting source-key miss and conflicting instruction lineage reproduced the superseded-instruction failure. The captured run was interrupted at its 240-second budget; it was not a successful continuation.

The fix sorts object keys only for process-local execution/round hashes and instruction lineage, at two unique checksum-pinned anchors. It preserves every JSON value, array order and string byte representation; it does not alter request content, capabilities, retirement ordering or durable checkpoint hashes. Existing encrypted checkpoint records keep their original schema and validation. This does not establish that legacy checkpoint source matching is immune to all later key reordering.

The real pinned registry/broker regression first failed before the fix. After the fix, reordered-content compaction finds the original source, revokes its capability, waits for physical teardown and starts read-only summarization without injecting a tool completion. Changed content, missing identity, changed reasoning and separate provider namespaces retain their conservative behavior. Pinned restart, durable recompaction and tamper controls also passed. Live post-fix continuation and complete large-window retention still require separate evidence.
